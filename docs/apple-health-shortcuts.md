# Appleヘルスケア → iOSショートカット → QnapSelfCare

## 決定した範囲

FIT 5 Pro → HUAWEIヘルスケア → Appleヘルスケア → iOSショートカット
→ LAN/Tailscale上のSelfCareという経路を使用する。追加のBluetooth受信機、
HomeHub変更、iPhone専用アプリの署名、外部クラウドへの健康データ送信は不要。

対象は歩数、ウォーキング＋ランニング距離、アクティブエネルギー、心拍、SpO₂、睡眠の6項目。
体重・BMI・体脂肪率など体組成は対象外。既存OMRON記録、体重計算、活動計画を変更しない。
APIは許可リスト方式で、対象外が混ざればバッチ全体を400で拒否する。
体組成を黙って保存したり、自動的に既存測定へ変換したりしない。

## 段階と完了条件

1. **このPR：受信基盤** — 仕様、6項目の検証・正規化、一括永続保存、再送重複抑止、
   ページ付き確認API、バックアップ／復元、QPKG同梱、回帰テスト。
2. **次：実機ショートカット** — iOS上で各項目の値・単位・記録元・睡眠区分を確認し、
   配布用ショートカットと設定画面を完成させる。実機未確認を「自動同期完成」としない。
3. **次：閲覧** — 活動、心拍／SpO₂、睡眠画面、期間集計、既存カーソルUIへの統合。
   高頻度サンプルを既存の最新2000件枠へ混ぜない。

XML/ZIP取り込み、Health Auto Export互換、Apple側削除の自動追従、日次集計の受信、
ECG/HRV/ストレス、診断、自動実行機能の追加はこのPRの範囲外。
既存Webトップ・OMRON同期・エネルギー計算・起動処理は維持する。

## API v1

`POST /api/apple-health/import`

ヘッダー：`Content-Type: application/json`、`X-SelfCare-Request: 1`。
既存の32 MiBリクエスト上限、Content-Length必須、同一オリジン方針を維持する。
カスタムヘッダーはログイン認証ではない。公開インターネットへ直接公開せず、既存のLAN/Tailscale内で利用する。

```json
{
  "schema": 1,
  "user_id": "登録済み利用者ID",
  "samples": [
    {
      "metric": "heart_rate",
      "start_at": "2026-10-26T07:00:00+09:00",
      "end_at": "2026-10-26T07:00:00+09:00",
      "value": 72,
      "unit": "bpm",
      "source": "HUAWEIヘルスケア：グローバル"
    }
  ]
}
```

トップレベルは上記3フィールドのみ。1バッチ0〜50,000件。空配列は何も変更しない。
通常は全項目を1回でPOSTする。50,000件または32 MiBを超える場合は期間を分ける。日次合計ではなく**元サンプル**を送る。
送信元アプリに記録された開始・終了時刻を使い、送信時刻に置き換えない。
タイムゾーン付きISO 8601必須。内部UTC、マイクロ秒を保持。

| metric | value | unit |
|---|---|---|
| steps | 整数の歩数 | count |
| walking_running_distance | 区間距離 | m（kmも受付） |
| active_energy | 区間活動エネルギー | kcal（kJも受付） |
| heart_rate | 心拍数 | bpm |
| oxygen_saturation | 酸素飽和度 | %（0〜1形式は明示的にfraction） |
| sleep | awake / in_bed / asleep_unspecified / core / deep / rem | null |

睡眠は終了>開始、その他は終了>=開始。睡眠段階は実際に取得できた区分のみ。
数値からSpO₂の単位を推定しない。活動カロリーを総消費カロリーへ加算しない。
許可値の範囲は入力形式の防御用であり、医学的正常範囲ではない。

各サンプルには任意で `source_id`（取得できる場合のみ元サンプルの不変ID）、
`device`（取得できる場合のみ元機器の文字列）を追加できる。
`source` は実際の記録元。取得できない場合は `unknown` を明示し、HUAWEIとは推定しない。
受信側は記録元による自動選別はしない。ショートカットでHUAWEI由来に絞る。
同じレコードにsource_id/deviceを途中から付加すると重複識別が変わるため、設定を固定する。

成功200：`{"inserted":1,"duplicates":0,"received":1}`。
全サンプルを検証し、一括トランザクションを永続コミットしてから成功を返す。
不正400、必須ヘッダーなし403、DB保護／DB障害503。失敗時は全件ロールバック。
接続切断で応答を失った場合も同じバッチを再送できる。

元IDがある場合は利用者＋項目＋記録元＋元IDを識別子とする。
同じIDで内容が変わった場合は上書きせず400を返す。
元IDなしでは正規化後の内容全体（出所・区間・値等）を識別子とする。
そのため内容が訂正された記録や、全く同じ内容の別サンプルは完全には識別できない。
これはappend-only v1の制限。空結果・欠落・権限不足を削除指示とは解釈しない。

`GET /api/apple-health/samples?user_id=...&since=...&until=...&limit=200&offset=0`
は保存確認用。limitは1〜1000、offsetは0〜10000000。
since/untilは任意のタイムゾーン付きISO 8601（URLエンコードする）。
区間はend>=since、start<untilに一致するもの。日をまたぐ睡眠も取得する。
`total` と `samples` を返す。各サンプルに `received_at` を付与。
複数ページ取得中に新規追加される場合は一貫したスナップショットではない。
このAPIの件数を日次歩数や睡眠時間にそのまま換算しない。

## ショートカット組み立て・自動化計画

1. SelfCareで取込先利用者を登録し、`GET /api/users` のIDとNAS URLを設定する。
2. 「ヘルスケアサンプルを検索」で6項目を個別に検索する。体組成は検索しない。
3. 読み取り権限を許可。記録元フィルターが利用できればHUAWEIに限定する。
4. 各サンプルの詳細から値、単位、開始、終了、記録元を取得。辞書を組み立てる。
   睡眠は表示名を上記英語enumに変換。区分不明は捏造せず停止して設定を確認する。
5. 「URLの内容を取得」をPOSTにし、上記ヘッダーとJSON本文を設定。
6. まずロック解除状態で手動送信。成功レスポンスと確認APIで件数・値を照合する。
7. 自動化は毎日夕方などを候補にする。iOSの「すぐに実行」が利用できるトリガーを使用。
   ロック中のHealthKit読み出し、背景実行時間、低電力モード、LAN到達性に制約があり、
   定刻実行は保証しない。手動実行も残す。HUAWEI→Appleの同期完了を確認してから送る。
8. 簡易版は毎回直近7日を重ねて送信し、前回成功時刻のファイル管理は行わない。
   失敗時は同じショートカットを再実行する。7日以上の未同期や古い遅延追加は、
   期間を広げた手動補完が必要。固定7日で無期限の取りこぼし防止は保証しない。
   空結果は権限拒否とも区別できないため完了証明に使わない。
   NAS側の最終受信時刻は全項目の同期完了時刻ではない。

実機確認待ち：6項目の詳細取得可否、睡眠区分、出所フィルター、SpO₂単位、
大量一括送信時の実行時間、自動化時のロック状態／失敗通知。
設定手順は設計案であり、このPRでは署名済み .shortcut ファイルを配布していない。

## 保存・復元・後続表示

既存SQLite内の専用テーブルに保存。測定データはRAMのみで成功扱いにしない。
既存SQLiteのWAL、synchronous=FULL、破損保護を継承。アクセスログの抑制を維持。
同じデータの再送ではサンプルを更新しない。定期スキャンや追加バックグラウンド処理は作らない。

JSONバックアップはschema 2へ更新し、新テーブルを含める。schema 1の復元も継続。
旧版アプリはschema 2を拒否するため、新データの黙った脱落を防ぐ。
外部サンプルには既存measurementsの10万件制限を適用しない。
ただしJSON出力は全件をメモリに構築しHTTP復元は32 MiB上限があるため、長期・大容量運用では
既存のSQLiteスナップショットZIPバックアップ／オフライン復元を使用する。
新データを追加したDBを旧版へダウングレードして運用しない。

次の表示PRでは出所選択、元サンプルと集計の分離、睡眠の重複区間除外、
欠測表示、期間集計の上限・性能を実装する。iPhoneとHUAWEIの歩数を合算しない。
検証には再送、単位、タイムゾーン、ユーザー分離、原子的失敗、保護モード、再起動、
旧DB移行、JSON往復、SQLiteスナップショット、既存OMRON不変を含める。

## 参考

### ショートカットでの具体的な送信例と切り分け

まず心拍の直近1日・最大10件で試す。アクションの流れ：
「ヘルスケアサンプルを検索」→「各項目を繰り返す」→「ヘルスケアサンプルの詳細を取得」
（値・単位・開始日・終了日・ソース）→「日付をフォーマット」（ISO 8601）→「辞書」
→「変数に追加」（samples配列）→「URLの内容を取得」（POST、JSON）。
schemaは数値1、samplesは辞書の配列、valueは数値（睡眠だけ文字列）にする。
配列や辞書を引用符付き文字列に変換しない。source_idは通常の詳細取得では保証されないため省略する。
sourceは実際のソース名を使用する。日本語の名称やアクションの表示はiOSによって異なる。
日付フォーマットでISO 8601が選べない場合は `yyyy-MM-dd'T'HH:mm:ssXXX` を使い、
タイムゾーンを含める。表示値と単位を確認し、距離やSpO₂を値の大きさだけで変換しない。
睡眠の区分取得は実機で確認する。APIのunit:nullを空文字や文字列"null"へ置き換えない。

最初は最終JSONを「クイックルック」などで確認し、NASへ送信する。
接続のみの確認は `{"schema":1,"user_id":"登録済みID","samples":[]}` でよい。
空送信は測定データを追加・削除せず、ヘルスケア権限や実サンプルの取得成功を証明しない。
実送信前にHUAWEIアプリの同期を済ませる。自動化は「時刻」等で実行できるが、
読み出しはロック状態に制約があるため、HUAWEIアプリを閉じたとき等のトリガーも候補。
閉じたこと自体は同期完了を保証しないため、7日分の再送と手動ボタンを残す。

### 設定画面の受信デバッグ

設定・バックアップ → 「iPhoneショートカット連携・受信デバッグ」を開く。
送信先URLを確認し、「10分間の記録を開始」→ iPhoneから送信 → 「受信状況を更新」。
受信日時、HTTPステータス、保存／重複件数、エラー、受信本文プレビューを確認できる。
「ログをダウンロード」でJSON出力。「停止・消去」で記録停止とメモリ内ログ削除。
「ログを消去」は記録を継続したまま現在のログだけを削除する。
ダウンロードしたファイルは自動消去されないため、共有前に健康情報を確認する。

- 初期OFF。最新20件、本文は先頭8192バイトまで。切り詰めは表示用でありAPIの入力は切り詰めない。
- RAMのみ。10分後のタイマーで停止・消去し、再起動でも消える。通常ログ・DB・バックアップには含めない。
- 再度開始すると既存ログを消去し10分の期限を更新する。受信中に停止したリクエストのログは後から追加しない。
- 対象は `POST /api/apple-health/import` のみ。JSON不正も記録。ヘッダー検証で失敗した場合は本文を読み取らない。
- Authorization等のヘッダー、IP、URLクエリーはログに含めない。本文に入れた内容は健康情報も含めて記録される。
- `GET /api/apple-health/debug`、`GET /api/apple-health/debug/download` で確認・出力。
- `POST /api/apple-health/debug` + `{"action":"start"}` / `stop` / `clear` で操作。
  既存のJSON・X-SelfCare-Requestヘッダーが必要。設定画面のボタンからも操作できる。
- OFF時は本文をデバッグ用に複製しない。画面の自動ポーリング・ディスク追記は追加しない。
- ログがない場合、リクエストがNASに到達していない可能性がある。DNS、LAN/Tailscale、
  ポート、iPhoneのロック・権限・自動化を確認する。未到達の失敗はNAS側では記録できない。

## 簡易入力 schema 2（2026-10-27）

同じ POST /api/apple-health/import で受け付ける。schema 1 の形式と応答は維持。
グループごとに項目名・記録元・単位を一度指定する。
各レコードの必須フィールドは start / end / value の3つ。
これはHealthKitオブジェクトの直接送信ではなく、ショートカットで抽出した未集計データ。
受信後、検証・正規化して保存する。元JSON全体を恒久保存する機能ではない。

以下は構造説明用の合成データ（実測値ではない）。

~~~json
{
  "schema": 2,
  "user_id": "登録済み利用者ID",
  "groups": [
    {
      "type": "歩数",
      "source": "HUAWEIヘルスケア：グローバル",
      "unit": "歩",
      "samples": [
        {"start": "2026-10-27T06:11:00+09:00", "end": "2026-10-27T06:12:00+09:00", "value": 40}
      ]
    },
    {
      "type": "睡眠",
      "source": "HUAWEIヘルスケア：グローバル",
      "unit": "",
      "samples": [
        {"start": "2026-10-27T04:09:00+09:00", "end": "2026-10-27T04:40:00+09:00", "value": "レム"}
      ]
    }
  ]
}
~~~

### ショートカットの組み立て

1. 「現在の日付」を T に保存。「日付を調整」で7日前の開始日 S を作る。
2. 「ヘルスケアサンプルを検索」で項目ごとに S〜T の元サンプルを検索。
   件数制限OFF、集計・グループ化なし。HUAWEIのソースだけに限定する。
   次の検索に前項目の結果を渡さないよう「何もしない」を挟み、独立して検索する。
   境界をまたぐ睡眠は終了>=S、開始<Tの重複区間を含める。検索UIで指定できない場合は
   取得開始を余分に1日戻してから絞り込む。1日を超える区間はさらに広げる。
   境界の実機挙動は要確認。区間の時刻を日境界で切り詰めない。
3. 「各項目を繰り返す」で開始日、終了日、値を取得する。
   日付はタイムゾーン付きISO 8601にフォーマット。数値型または数値だけの文字列で保持。
   辞書 start / end / value を作り、繰り返し結果を samples にする。
   「40歩」「96%」など単位付き文字列を value に入れない。
4. type / source / unit / samples の辞書を作る。このブロックを複製して6項目にする。
   samples は辞書配列または後述のJSON文字列形式で渡せる。
   ソースフィルターでHUAWEIに限定したことを確認できる場合のみsourceを固定できる。
   ソースで絞らない場合はsourceをunknownとし、出所が混在する制約に留意する。
5. 6グループをリストにし、schema（数値2）/ user_id / groups をJSON本文にする。
   POST、Content-Type: application/json、X-SelfCare-Request: 1。
   「URLの内容を取得」は繰り返しの外に1つだけ置く。
6. 成功応答のreceivedと取得総数、inserted + duplicatesの一致を確認する。
   空配列が成功しても、全項目取得できた証明にはしない。失敗・不一致では完了表示しない。
7. 毎日の時刻オートメーションにこのショートカットを登録する。
   最初はロック解除状態で手動実行し権限を許可。HUAWEI→Appleの同期完了後に実行する。
   ロック中の読み取りや大規模なループの背景実行は保証できない。
   実機で6項目の値・睡眠区分・所要時間を確認してから日次運用する。

前回時刻の保存、端末側の単位換算・睡眠区分変換、通常時の分割処理は不要。
APIは50,000件超過や32 MiB超過を切り捨てず400で拒否する。
通常は7日分を一括送信。上限に達した場合は取得期間を区切って手動補完する。
自動分割・署名済みショートカットの生成は未実装。

### 受け付ける値

type はschema 1のmetric名、または以下の完全一致名：
歩数 / ウォーキング＋ランニングの距離 / アクティブエネルギー /
心拍数 / 取り込まれた酸素のレベル / 睡眠。
1リクエスト最大6グループ、同じmetricの複数グループは不可。
体重・BMI・体脂肪などは空グループでも拒否する。

unit はschema 1の単位に加えて 歩 / 拍/分 / 拍／分 / パーセント / キロカロリー。
睡眠のunitは空文字（JSON nullをショートカットで作る必要がない）。
各レコードに任意のunitを指定するとグループの単位より優先する。
距離のm/kmが混在する場合はサンプルの実際の単位をレコードに付ける。
数値から単位を推測しない。SpO₂の96と0.96は、それぞれ%とfractionを明示する。
「%」を付けるだけで0.96を96にする処理はない。

睡眠value はschema 1の英語区分、または以下の完全一致名：
覚醒→awake、ベッドにいた時間→in_bed、睡眠→asleep_unspecified、
コア→core、深い→deep、レム→rem。
日本語は明示的な対応表であり、全iOS表示名の実機確認済みという意味ではない。
未知の名称はエラーとして追加調査し、値を推測して保存しない。
任意のsource_id/deviceはschema 1と同じ。画面に表示されるSyncIdentifierを
ショートカットから取得できるとは限らないため必須にしない。

### 応答・保存・デバッグ

schema 2 の成功応答は inserted / duplicates / received に加え、
counts（6項目別の受信件数。重複を含む）、start_at / end_at（UTCの最小開始・最大終了）、
processing_ms（変換から保存まで。HTTP受信時間を除く）を返す。
空結果の日時はnull。これらの件数は日次集計値や同期の完全性を証明しない。
schema 1との相互再送でも正規化後の内容が同じなら重複として扱う。

設定画面の受信デバッグにもこの要約を表示・ダウンロードする。
ログは初期OFF、10分・最新20件・本文先頭8 KiBのRAM制限を維持する。
不正サンプルは1始まりの groups[n] samples[n] の位置を返す。
全件検証とトランザクションで部分保存を防止する。
同じ元IDの内容変更は従来どおり拒否。訂正・削除追従はこの変更の対象外。

### 検証

50,000件の異なる時刻のサンプルをHTTP経由で一括保存・再送し、
再送がすべて重複になることをテストする。
50,001件・本文上限超過・不正値・元ID競合を拒否する。
schema 1互換、6項目、混在単位、日本語睡眠、空結果、再起動後の保存、
体組成除外、デバッグ要約も確認する。NAS/iPhone実機性能は別途測定する。

## ショートカットの文字列送信互換

schema 2では、groupsとsamplesに通常の辞書配列のほか、JSON文字列、
単一のJSON辞書、またはJSON辞書を改行で並べた文字列を受け付ける。
配列要素がJSON辞書文字列の場合も対応する。文字列の入れ子は最大4段。
実改行と、レコード間の文字列としての \n に対応する。壊れた末尾を無視しない。
samplesの各辞書だけは、誤って外側に括弧が1組追加された `{{"start":...,"end":...,"value":...}}`
も受け付ける。辞書を解析して直後の余分な閉じ括弧を確認するため、値の中の括弧は変更しない。
三重括弧、不足する括弧、余分な末尾、日時欠落は拒否し、バッチの一部だけを保存しない。
これはJSONの構造を復元する処理であり、任意のHealthKitオブジェクトの直接受信ではない。

数値項目のvalueは "72" などの数値文字列でもよい。正規化後は数値として保存する。
単位付き文字列、カンマ区切り、NaN、Infinity、真偽値は拒否する。
睡眠は従来の区分対応表を使う。schema 1は従来どおり厳密な入力を要求する。
50,000件・32 MiB、全件検証、原子的保存、重複判定、体組成除外は維持する。

必須情報は変わらない：
- グループ：type、source、unit、samples
- 各記録：start、end、value

数値だけの改行リストは日時・項目・単位を復元できないので保存せず400を返す。
時刻を送信時刻や等間隔から推測しない。元データに日時がある形式で再送する。
ログは先頭8 KiBで切れるため、切れたログ本文自体を再インポートしない。

簡易な作成指示（心拍）：
「ソースフィルターなしで過去1日の心拍を検索。各サンプルから開始日時・終了日時・
値を取得し、start/end/valueのJSON辞書を1行ずつ作る。日時はタイムゾーン付き
ISO 8601。行を改行で結合してsamplesに入れる。type=heart_rate、source=unknown、
unit=bpmとともにグループ辞書を作り、schema=2/user_id/groupsとして一括POSTする。
グループやsamplesがJSON文字列でもサーバーが解析する。数値だけを送らない。」

sourceフィルターは必須ではない。出所を取得できず混在する場合はunknownを使い、
HUAWEIと偽って固定しない。ただしunknownでは異なる出所の同一内容を区別できず、
活動量の重複計上防止や出所別表示に制約がある。既存データのsource設定を変えると
重複識別が変わるため、試験後は設定を固定する。
