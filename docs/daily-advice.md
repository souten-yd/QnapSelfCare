# 毎日のアドバイス（自動作成）

NAS上のQnapSelfCareが、毎日決まった時刻にその日の記録を直前7日間と比べ、AIから生活・減量のアドバイスを受け取ります。時刻・AIの接続先・AIの稼働状況は設定の「AI」タブ、結果・相談は健康サポートの「AI」タブにあります。

## 動き

1. 1分ごとに時刻だけを確認します（設定はメモリにキャッシュし、ディスクを起こしません）。
2. 設定時刻（初期値 **2:00**）を過ぎたら、その日の分がまだない利用者ごとに作成します。
   - 12時より前の時刻は **前日分**、12時以降は **当日分** を評価します。
   - NASが止まっていた場合は、予定時刻から6時間以内なら起動後に作成します。
3. まず記録の比較（AIなし）を作ります：歩数・活動エネルギー・運動時間・睡眠時間・摂取・収支・体重・最高血圧を、直前7日の平均と比べて「いつもどおり／多め／少なめ」を判定します。
4. 比較結果・評価指標・計画などを添えて、AIに「1日の振り返りと翌日のアドバイス」を依頼します。回答は「要点／根拠になったデータ／提案（最大3つ）／注意」の形です。
5. 結果は利用者・日付ごとにDBへ保存し、健康サポート（AIタブ）とHomeに表示します。

## AIへの送り方

| 接続先 | 方式 |
|---|---|
| QnapAssistant | 非同期ジョブAPI（`/api/llm/jobs`）。15秒ごとに状態を確認し、最大2時間待ちます（QnapAssistant側の生成タイムアウト3600秒＋モデル読込に余裕を加えた値）。 |
| ControlDeck・その他のローカルLLM | 従来の同期API（最大300秒）。 |
| OpenRouter（外部） | 「外部サービスにも自動で送信する」をオンにした場合だけ送ります。オフのときは記録の比較だけを作成します。 |

## 送らない・やり直す条件

- その日の記録が1つもない → 作成しません（AIにも送りません）。
- AIの接続先が未設定 → 記録の比較だけを保存します。
- AIが他の相談を処理中・混雑（429） → 10分後に再試行します（最大3回）。
- QnapAssistantの再起動などでジョブが失われた → 失敗として記録し、自動で再送はしません（QnapAssistantの方針に合わせています）。「昨日分を今すぐ作成」で作り直せます。
- SelfCareの再起動で作成中だったもの → 失敗として記録します。

## QnapAssistant側の変更

不要です。既存の非同期ジョブAPI（v0.5.9以降）で、受付・状態確認・結果取得・キャンセルの必要な機能がそろっています。1件ずつ順番に処理するため、待ち行列の上限（実行中1件＋待機4件）を超えません。

## API

- `GET /api/ai/daily-settings` / `POST /api/ai/daily-settings` `{enabled, time: "HH:MM", allow_external}`
- `GET /api/wellness/advice?user_id=` → 最新と直近14件
- `POST /api/wellness/advice/run` `{user_id, day: "yesterday" | "today"}` → 202（バックグラウンドで作成）

設定はJSONバックアップに含まれます。作成済みのアドバイスは再作成できるため、JSONバックアップには含めません（定期バックアップのDBには含まれます）。

## AI処理のバックグラウンド実行（300秒制限の解消）

以前は「計画のAI分析」「AIカロリー試算」「接続テスト」が同期API（最大300秒）で、QnapAssistantのモデル読込＋生成が300秒を超えるとエラーになっていました。現在はすべてのAI処理をSelfCare内のバックグラウンド処理として実行します。

1. ブラウザは `POST /api/ai/jobs`（`kind`: `consult` / `meal` / `test`）で依頼し、IDを受け取ります。
2. `GET /api/ai/jobs/status?id=` を数秒ごとに確認します（順番待ち・モデル読込中・生成中・経過時間・空きRAM）。画面を閉じても処理は続き、再読み込みすると相談の続きを表示します。
3. QnapAssistantは非同期ジョブAPIで最大2時間待ちます。ほかの接続先は従来の同期API（最大300秒）です。
4. AI処理（相談・夜間のアドバイス・計画の点検）は1件ずつ順番に実行し、NASのモデルを取り合いません。
5. 処理内容（質問・回答）はメモリにだけ保持し、完了30分後に破棄します。`POST /api/ai/jobs/cancel` で中止できます。

## 減量計画の点検と修正案（同意して適用）

夜間のアドバイスのあとに、減量計画の点検も行います（週1回まで。新しい計画は14日間は点検しません）。「今すぐ点検する」で手動でも実行できます。

**見直しが必要と判断する条件**：計画線より0.5kg以上重い／今のペースで目標日に間に合わない／減量ペースが速すぎる・増加している／直近3週が横ばい／逆算した摂取量が安全な下限を下回る／目標日を過ぎた。

**修正案**（同じエネルギーモデルで目標日の体重を試算）：
- 案A 目標日を見直す：今の生活のまま、安全なペース（観測ペースが週0.25〜1.0%ならそのペース、そうでなければ0.5%）で目標日を再設定。
- 案B 摂取量を見直す：目標日はそのまま、必要な標準摂取量に変更。安全な下限（1200kcalと推定基礎代謝の高い方）を下回る、または週1%を超える場合は出しません。
- 案C 運動を増やす：目標日と摂取はそのまま、速歩相当（4.3 MET）の運動を1日30分追加。

目標日に1kg以上届かない案、目標がBMI下限を下回る場合には注意を表示します。AIが理由とトレードオフを説明し、1つを推奨します（AIがない場合は規則で推奨）。

**計画は自動では変わりません。** 「この案で計画を更新」を押し、確認ダイアログで同意したときだけ、新しい計画として保存します（理由つきで履歴に残り、元の計画も残ります）。案を作った後に手動で計画を変えた場合、その案は無効になります。

## AIの稼働状況（止まっているか・進んでいるかの確認）

AIは1件ずつ順番に動きます。設定 →「AI」タブの「AIの稼働状況」で、いま何が動いているかを確認できます。

| 表示 | 意味 |
|---|---|
| 実行中 | AIを使っている処理（例：毎日のアドバイス（利用者・日付）、AI相談、接続テスト）。夜間の自動処理には「（自動）」と付きます |
| 段階 | 順番待ち／モデルを読み込み中／回答を生成中と、その経過時間 |
| QnapAssistantの最終応答 | SelfCareが最後にQnapAssistantから状態を受け取ってからの時間。正常ならおおむね15秒以内で更新されます |
| 自動打ち切りまで | 開始から2時間で必ず打ち切り、次の処理に進みます |

- **進んでいる**：「最終応答」が数秒〜十数秒前で、段階が「読み込み中→生成中」と進む。
- **止まっている可能性**：「最終応答」が3分を超えると警告を表示します（NASやQnapAssistantの停止・再起動など）。待っても2時間で自動的に打ち切ります。すぐ止めるには「実行中の処理を中止」（QnapAssistant側の処理も取り消します）。
- 待っている依頼には「〇〇の完了を待っています（その処理は△△・経過時間）」と、何を待っているかを表示します。画面からの依頼は2時間待っても空かない場合に取り消します。
- 画面からの依頼は夜間の自動処理より優先します（夜間処理は利用者ごとの区切りで順番を譲ります）。手動の「昨日分を今すぐ作成」「今すぐ点検する」も画面からの依頼として扱います。

## 予定時刻を過ぎた場合の取り戻し

NASが止まっていた・更新で再起動した等で予定時刻（初期値2:00）に動けなかった場合、**予定時刻から6時間以内**なら起動後に作成します。6時間を過ぎていた場合（例：19時に更新した）は、日中に重いAI処理を始めないよう自動作成を見送り、「予定時刻を大きく過ぎたため自動作成を見送り」と表示します。「昨日分を今すぐ作成」で手動作成できます。

## 設定の場所

- **設定 →「AI」タブ**：AIの稼働状況（実行中の処理・中止）、AIの接続先・APIキー・接続テスト、毎日のアドバイスの自動作成と時刻。
- **健康サポート →「AI」タブ**：毎日のアドバイス（結果・手動作成・履歴）、AI相談。
- メインメニューの順番：ホーム → 健康 → 記録 → 機器 → 設定。

## v0.3.54 日次AIアドバイスの診断

QnapAssistant **v0.5.10以降**が、内部SSEで受け取った回答の途中
テキストと生成タイミングをRAMに短期保持します。従来のQnapAssistantの
OpenAI互換APIと日次アドバイス生成の非同期処理はそのまま維持します。

- 日次アドバイスの成功/失敗が確定した時点で、QnapAssistantの
  `GET /api/llm/jobs/{id}/diagnostics`を取得し、安全な項目のみ
  `ai_daily_advice.diagnostics` にJSON保存します。
- 要約にはエラーコード、推論時間、最初のトークンまでの時間、
  最後の出力からの経過時間、応答チャンク数、バックエンドが報告した
  token数、出力バイト数、終了理由を含みます。
- **形式警告は生成失敗と分離**。回答が完成しても「要点」「根拠」
  「提案」「注意」の見出しが不足したら警告を表示します。
  形式不一致だけで回答を破棄しません。
- 健康サポート → AI → 毎日のアドバイス → **AI実行診断・原因解析**
  に診断要約と対処案を表示。**診断要約をJSONで保存**で出力可能。
- **生成原文を一時取得**はユーザーが押した時だけ。
  SelfCareはPOST `/api/wellness/advice/diagnostics/raw`
  `{user_id,day}` でQnapAssistantのRAM上の出力を代理取得します。
  リクエストには既存の `X-SelfCare-Request: 1` が必須です。
  原文をディスクへ書き込んだり、定期ポーリングで取得したりしません。
- 原文はQnapAssistantジョブ完了後約15分で破棄され、
  サービス再起動でも失われます。**診断要約のみ**再起動後も
  自分のNASのSQLiteに保存されます。
- SQLiteの既存行には安全な増分マイグレーションで
  `diagnostics`, `diagnostic_job_id`を追加します。後者は原文取得
  に必要な短期のcapability IDなので通常の履歴APIには表示しません。
- 推論がタイムアウトしただけではOOM断定不可。メモリや
  バックエンドの詳細ログと突き合わせて原因を判断してください。

NAS側のポート11435とSelfCareの17863は外部へ公開せず、
信頼できるLAN/VPN内だけで使用してください。診断原文の内容を
外部共有する際は健康情報の有無を確認してください。

## AIに送る内容（小さいモデル向けの簡潔な形式）

QnapAssistantのモデルはコンテキストが4096トークン程度のことが多く、以前のJSON形式（約7,000文字）では入力だけで上限を超え、最初の文字が出る前に時間切れになることがありました（診断: `generation_first_token_timeout`）。

現在は `prompt_text.py` が、必要な数値だけを短い日本語の行にまとめて送ります（毎日のアドバイスで約1,300文字）。

- 優先順：対象日の記録と7日平均の比較 → 計画の修正案 → 現在の値 → 目標・計画 → お知らせ → 評価指標 → 週ごとの体重 → 食事メモ → 最近の活動。
- 上限（約1,800文字）を超える部分は、優先度の低いものから省きます。
- 評価指標の説明文は送りません。夜間の処理では「目安内」以外の指標だけを送ります。
- 続けて質問する場合の前の相談は、新しいものから合計約1,200文字までです。

それでも時間切れになる場合は、QnapAssistant側でコンテキストを8192に増やすか、より小さいモデルを選んでください。

## AVXのないCPU（Celeron J3455など）での注意

TS-253Be（Celeron J3455）のQnapAssistantは、AVXなしのCPU向けにビルドされています（SSE4.2まで）。実機ログでは処理速度が次のように大きく違いました。

| モデル | 入力の読み込み | 生成 |
|---|---|---|
| Qwen3-0.6B Q8_0 | 約9〜16トークン/秒 | 約1〜8トークン/秒 |
| Qwen3-4B Q4_K_M | 約0.3トークン/秒 | 約0.1トークン/秒 |
| Qwen3-8B Q4_K_M | 約0.15トークン/秒 | 約0.1トークン/秒 |

- Q4_K_Mなどの「K」量子化は、AVXがないと高速な計算経路が使えず、極端に遅くなるとみられます。
- 約700トークンの依頼でも、4B Q4_K_Mでは読み込みだけで40分以上かかります。
- 夜間のアドバイスには、Qwen3-0.6B/1.7BのQ8_0か、Q4_0形式のモデルを推奨します。
- 4Bを使う場合も、K量子化ではなくQ4_0を選んでください。
- QnapAssistantの `llama-bench` で、量子化ごとの速度を比べられます。

夜間のアドバイスでAIが失敗した夜は、続く計画の点検をAIなし（規則による判定）で行い、長いAI処理を続けて始めません。
